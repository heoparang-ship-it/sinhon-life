# 신혼생활 결제 도입 전 설계 문서

작성일: 2026-06-05

상태: 설계 초안. 코드 구현 금지. 법무, 보안, 운영 승인 후에만 25-B 샌드박스 구현으로 이동한다.

## 1. 결제 도입 원칙

- 결제는 상담 신청, 가격 투명성, 비교방 공동 승인 흐름이 충분히 검증된 뒤 도입한다.
- 신혼생활는 카드번호, CVC, 계좌번호를 직접 저장하지 않는다.
- 결제 대상은 파트너와 가격 버전 검증이 끝난 상품의 예약금으로 제한한다.
- 결제는 계약 확정이 아니라 예약/상담 확정 보증금 성격으로 시작한다.
- 모든 결제 상태 변경은 idempotency key, 상태 이력, audit log를 남긴다.

## 2. 결제 대상 상품

결제 대상:

- 검증 상태가 `verified`인 파트너 상품.
- 유효기간이 지나지 않은 `OfferPriceVersion`.
- 비교방에서 두 멤버가 모두 승인한 상품.
- 운영자가 예약금 결제 가능으로 명시한 카테고리.

초기 후보:

- 스튜디오 촬영 예약금.
- 예식 상담 예약금.
- 입주/가전 상담 예약 보증금.

## 3. 결제 비대상 상품

- 정책/혜택 신청 대행 비용.
- 대출, 금융상품, 보험, 투자성 상품.
- 가격 버전이 미검증, 반려, 만료 상태인 상품.
- 파트너가 환불/취소 정책을 제출하지 않은 상품.
- 최종 계약금, 잔금, 정산 자동화 대상 금액.

법무 검토 필요:

- 예약금이 실제 계약금으로 간주되는지.
- 단순 상담 예약 보증금의 환불 의무.
- 파트너 약관과 신혼생활 약관의 책임 범위.

## 4. 예약금 구조

초기 구조:

- 사용자가 비교방에서 둘 다 승인한 카드 1개를 선택한다.
- 서버가 결제 준비 API에서 `PaymentIntent`를 만든다.
- 결제 금액은 `OfferPriceVersion`의 `reservationDepositAmount` 또는 운영자가 설정한 고정 예약금이다.
- 예약금은 상품 총액에서 차감되는지, 별도 수수료인지 상품별로 명시한다.

필수 표시:

- 예약금 금액.
- 총 예상 금액.
- 예약금 차감 여부.
- 취소 가능 시점.
- 환불 가능/불가 조건.
- 파트너명과 상품명.

## 5. 취소·환불 정책

초기 상태값:

- `payment_ready`
- `payment_requested`
- `paid`
- `cancel_requested`
- `canceled`
- `refund_requested`
- `refunded`
- `refund_rejected`
- `failed`

환불 기본 원칙:

- 결제 당일 또는 파트너 확정 전 취소는 전액 환불을 기본 후보로 둔다.
- 파트너가 예약 확정을 수락한 뒤에는 상품별 취소 정책을 따른다.
- 환불 거절은 반드시 운영자 사유와 파트너 근거를 남긴다.

법무 검토 필요:

- 전자상거래 청약철회 예외 적용 여부.
- 예약금 환불 불가 문구의 유효성.
- 파트너 귀책, 사용자 귀책, 플랫폼 장애 귀책 구분.

## 6. 파트너 정산 구조

MVP 제외:

- 자동 정산.
- 파트너별 세금계산서 자동 발행.
- 부분 정산, 수수료 자동 차감.

초기 운영 구조:

- 결제 성공 내역은 관리자 화면에서 확인한다.
- 정산은 운영자가 수동으로 검수한다.
- 파트너별 정산 상태는 `pending`, `approved`, `paid`, `held`, `disputed`로 관리한다.

필수 데이터:

- 결제 금액.
- PG 거래 ID.
- 파트너 ID.
- 상품 ID.
- 가격 버전 ID.
- 결제 상태 이력.
- 환불/취소 사유.

## 7. PG 연동 방식

권장 방식:

- PG hosted checkout 또는 SDK를 사용한다.
- 카드번호와 인증 데이터는 PG가 직접 처리한다.
- 서버는 결제 준비, 콜백 검증, 상태 조회만 담당한다.

필수 서버 처리:

- `PaymentIntent` 생성.
- idempotency key 검증.
- PG 결제 요청 ID 저장.
- PG callback signature 검증.
- 서버 측 결제 상태 재조회.
- 성공/실패/취소 상태 전이 기록.

운영 금지:

- 실결제 운영키를 로컬이나 테스트 환경에 사용 금지.
- 카드번호, CVC, 계좌번호 직접 입력/저장 금지.
- PG callback을 signature 검증 없이 신뢰 금지.

## 8. 결제 보안

필수:

- 결제 준비 API는 CoupleMember 권한과 compare room `both_approved` 상태를 확인한다.
- 같은 compare card에는 활성 PaymentIntent를 하나만 허용한다.
- 모든 결제 준비 요청은 idempotency key를 요구한다.
- callback은 PG signature, timestamp, replay 방지를 검증한다.
- 금액은 클라이언트 입력이 아니라 서버의 가격 버전 스냅샷에서 계산한다.
- 상태 전이는 허용된 방향으로만 이동한다.

추가 권장:

- 결제 API rate limit.
- 관리자 결제 상태 변경 2인 승인.
- 결제 이벤트와 DecisionLog의 이중 기록.
- 장애 시 PG와 내부 상태 불일치 복구 배치.

## 9. 개인정보 처리

저장 가능:

- 내부 사용자 ID.
- 커플 ID.
- 비교방 ID.
- 파트너 ID.
- 상품/가격 버전 ID.
- PG 거래 식별자.
- 결제 금액과 상태.

저장 금지:

- 카드번호.
- CVC.
- 계좌번호.
- 주민등록번호.
- 상세 청구 주소.
- PG 인증 전문 원문.

검토 필요:

- 영수증 발행을 위한 이름/이메일/전화번호 최소 수집 여부.
- 파트너에게 전달되는 결제 완료 정보 범위.
- 결제 데이터 보관 기간.

## 10. 분쟁 처리

분쟁 유형:

- 사용자가 예약금을 환불받지 못했다고 주장.
- 파트너가 예약 확정 후 사용자가 취소했다고 주장.
- 결제는 성공했지만 신혼생활 상태가 실패로 남음.
- 중복 결제.
- 상품 가격/포함 항목 오표기.

운영 절차:

- 분쟁 접수 시 PaymentIntent, Transaction, callback log, DecisionLog를 함께 조회한다.
- PG 관리자 콘솔 거래 상태와 내부 상태를 대조한다.
- 파트너 응답 SLA를 기록한다.
- 환불 또는 정산 보류 결정은 사유와 담당자를 남긴다.

## 11. MVP 제외 범위

- 실결제 운영키 연동.
- 카드번호 직접 수집.
- 자동 정산.
- 세금계산서 자동 발행.
- 포인트, 쿠폰, 할부 프로모션.
- 부분 결제, 복합 결제.
- 파트너 셀프 환불.
- 결제 기반 추천 랭킹.

## 12. 25-B 진행 조건

25-B 샌드박스 구현 전 승인 조건:

- [ ] 담당: Legal - 예약금, 환불, 취소 문구 승인.
- [ ] 담당: Security - PG callback 검증과 idempotency 설계 승인.
- [ ] 담당: Privacy - 결제 관련 개인정보 수집·보관 범위 승인.
- [ ] 담당: Operations - 파트너 정산 수동 운영 절차 승인.
- [ ] 담당: Product - 결제 대상 카테고리와 비대상 범위 승인.
- [ ] 담당: Engineering - PaymentIntent 상태 전이표와 DB 스키마 리뷰 완료.

위 조건이 충족되기 전에는 결제 코드와 DB 모델을 구현하지 않는다.
